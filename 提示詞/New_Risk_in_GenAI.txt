# GenAI 時代下，測試需要管理的新風險｜圖片生成 Prompt

請製作一張 **16:9、4K、企業級簡報風格的橫向資訊圖表／風險心智圖**，主題為：

# **GenAI 時代下，測試需要管理的新風險**

整體視覺風格參考大型科技公司、資安公司、顧問公司的高階簡報，例如 Microsoft、IBM、Cisco、McKinsey、Deloitte 的技術架構與風險治理圖。

背景使用 **純白或極淺灰白色**，大量留白，資訊密度高但必須清楚、有秩序。使用：

- 細線
- 圓角矩形
- 扁平化 Vector Icon
- 色彩編碼
- 清楚層級
- 左 → 右閱讀動線
- 顧問式 Infographic Layout
- 高解析、銳利文字
- 不要 3D
- 不要照片
- 不要卡通風格

文字以 **繁體中文為主，搭配英文技術名詞**。

所有文字必須清楚可讀，禁止：

- 簡體中文
- 亂碼
- 拼字錯誤
- 任意改寫技術名詞

# 1. 需求、知識與 Context 風險

使用 **藍色 Blue**。

標題：

**需求、知識與 Context 風險**

英文：

**Requirement, Knowledge & Context Risks**

包含：

### 1. 規格不明確、AI 自行補充需求

右側說明：

**需求模糊、矛盾或遺漏時，AI 可能自行推測並補全，最終偏離真正需求。**

---

### 2. AI 不知道的事情，也可能直接給答案

右側說明：

**原本應該回答「我不知道」，AI 仍可能產生看似合理的 Content / Code / Test。**

---

### 3. AI 使用的 Context 可能已過期、錯誤或互相矛盾

右側加入：

**錯誤 Requirement、過時文件、錯誤註解、舊 API Example、舊版 RAG 資料，都可能被 AI 當成事實。**

底部強調：

**Garbage Context → Plausible but Wrong Output**

---

# 2. 程式碼實作與安全風險

使用 **綠色 Green**。

標題：

**程式碼實作與安全風險**

英文：

**Implementation & Security Risks**

包含：

### 1. AI 可能產生「看起來對，實際不對」的程式碼

右側列出：

**Boundary Error、Exception Handling 遺漏、Race Condition、Business Logic 錯誤、Hard Bug 等 Functional Risk。**

---

### 2. Functionally Correct ≠ Secure

中文補充：

**功能正確 ≠ 足夠安全**

右側：

**Authentication、Authorization、Injection、Secret、TLS、Input Validation、敏感資料相關問題，都可能被忽略。**

---

### 3. 黑箱狂喜：會寫 ≠ 代表就能信賴

右側：

**Unit / E2E Test 通過，不代表 Integration、Performance、Configuration、Reliability、Distributed System 或 Non-functional Requirement 都正確。**

---

# 3. 相依套件與供應鏈風險

使用 **橘色 Orange**。

標題：

**相依套件與供應鏈風險**

英文：

**Dependency & Supply Chain Risks**

包含：

### 1. AI 可能引用錯誤、過時或不安全的 Dependency

說明：

**可能引用不存在、已棄用、版本不相容，或存在已知 CVE 的套件。**

### 2. 套件搶註風險（Slopsquatting）

**攻擊者可能註冊 AI 容易推薦或幻想出的套件名稱，誘使開發者安裝惡意 Dependency。**

# 4. 測試設計與 Oracle 風險

使用 **鮮紅色 Red**。

這個區域是整張圖最重要的中央區域，尺寸比其他分類略大。

標題：

# **測試設計與 Oracle 風險**

英文：

**Testing & Oracle Risks**

包含 7 項：

---

### 1. AI 可能顯得很有道理，寫出「全部錯誤」的 Test Case

說明：

**AI 會根據 Implementation 與過去 Expected Result 產生測試案例，結果可能全部能執行、全部通過，但假設本身就是錯的。**

---

### 2. Code 與 Test 都由同一個 AI 產生，可能形成同源錯誤

說明：

**共享相同資料來源與推理偏誤，可能形成 Code 與 Test 一致但錯誤的 Common-Mode Failure。**

---

### 3. AI 可能產生錯誤的 Test Oracle / Expected Result

說明：

**AI 不只會產生 Test Case，也可能產生錯誤 Expected Result。**

強調：

**Code + Test + Expected Result 都可能同時錯。**

---

### 4. AI 可能產生「幾乎不會 Fail」的 Test Case

列出：

**Assertion 太弱、過度使用 Mock、不檢查真正期望結果，導致測試看似通過但沒有抓到風險。**

---

### 5. AI 可以產生大量 Test Case，但不代表風險有被覆蓋

說明：

**形式 Coverage 很高，不代表 Critical Risk、Business Risk、Boundary 或真正重要邏輯已被覆蓋。**

---

### 6. AI 造成 Test Case Inflation 與 Test Debt

說明：

**大量相似、冗長、低價值 Test Case 堆積，造成 Review 與 Maintenance Cost 上升。**

加入：

**Low Signal-to-Noise Ratio**

---

### 7. AI 可能針對既有 Test 過度擬合

英文：

**Test Overfitting**

說明：

**當 AI 同時看到 Implementation 與 Test，它可能最佳化的是「讓 Test Pass」，而不是「滿足 Requirement」。**

底部強調：

# **Pass the Test ≠ Satisfy the Requirement**

# 十一、整體核心論述

整張圖必須讓觀眾一眼理解：

**GenAI 帶來的不只是 New Risk，也會 Amplify Existing Risk。**

接著呈現：

**GenAI 提高產生 Code、Test、Expected Result 的速度，**
**但如果 Requirement Interpretation、Implementation、Test 與 Oracle 都來自相同 AI 或相同 Context，**
**就可能產生 Common-Mode Failure。**

也就是：

**Requirement 被理解錯**
**→ Code 忠實實作錯誤理解**
**→ Test 忠實驗證錯誤實作**
**→ Expected Result 也依照相同錯誤產生**
**→ Tests 全部 PASS**
**→ Product 仍然是錯的**

因此最後必須導向：

# \*\*GenAI Testing 的核心，不是產生更多 Test，

而是建立獨立的 Verification Evidence。\*\*
